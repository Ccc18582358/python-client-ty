# 爬虫逆向交接 · 盼之 + 螃蟹

> 用途：让下一个接手「爬虫 / 逆向」岗位的人快速了解这两个平台是怎么逆出来的、代码在哪、下次新平台怎么照着做。
> 最后更新：2026-09-04

---

## 一、一句话总结

盼之和螃蟹两个平台，**底层都是阿里云 WAF + 一套业务签名**。我们已经把「浏览器里跑的那套签名逻辑」逆向成**离线生成**（纯 Python + Node，不打开浏览器）：抓包拿到 WAF 状态（localStorage 里的几个 key）→ 用 Node 跑对应的混淆脚本 → 生成签名/解码参数 → 拼请求发出去。

- **盼之（pzds.com）**：列表接口 `goodsPublic/page` 是**完全匿名**的，离线参数已全打通。
- **螃蟹（pxb7.com 鲸汐）**：列表接口 `selectSearchPageList` 也**不需要登录**，只要一个 `user_id`，WAF 签名离线生成。

## 二、盼之 (pzds.com) 逆向

### 2.1 目标接口

| 用途 | 地址 | 是否要登录 |
|---|---|---|
| 商品列表（主） | `https://api.pzds.com/api/web-client/v2/public/goodsPublic/page` | ❌ 匿名 |
| 商品详情 | `https://www.pzds.com/goodsDetails/{goodsNo}/{catalogueId}` | ❌ 公开网页（吃 WAF） |
| 服务器时间 | `https://mcs.pzds.com/api/server/time` | ❌ |

### 2.2 逆出来的参数（6 类，全离线）

| 参数 | 是什么 | 生成函数 | 说明 |
|---|---|---|---|
| `Sign` | 业务签名（v18 WASM） | `sign_utils.generate_sign()` | 走 `pz_wasm_sign_runner.js`；**版本自动跟随**远程 `oss.pzds.com/mobileV3/wasm-config-prod.json`，无需手改 |
| `decode__1174` | 阿里云 WAF 解码参数 | `decode_utils.generate_decode_value()` | 走 `pz_waf_dynamic_runner.js`，~0.16s |
| `ssxmod_itna` / `ssxmod_itna2` | WAF cookie | `waf_cookie_generator.generate_cookies()` | LZW 压缩 + **自定义 base64**（字符集非标准） |
| `acw_tc` | WAF cookie | MD5 签名 | `md5("PZTimestamp=…&Random=…&accessKey=3qXyB7uf")`，GET `/api/server/time` |
| `deviceId` / `globalId` | 设备标识 | 随机 hex（`uuid4().hex`） | 服务端不校验具体值 |
| WAF 状态 | 挑战后的 localStorage | `refresh_waf_state.py` / `run_challenge()` | ~0.5s 解 challenge，写入 `config/waf_state.json` |

### 2.3 三条接口链（别混用！）

| 链 | 接口 | 参数 | 登录态 |
|---|---|---|---|
| **列表链（本次目标）** | `goodsPublic/page` | decode__1174 + ssxmod + acw_tc + **v18 签名** | 匿名 |
| 轻列表 | `general_goods/page` | 纯 MD5 + `token` header | 登录用户自己的在售列表 |
| 发布链 | `saveGoods` | 重型 WAF + v18 签名 + 新鲜 waf_state | **需登录态（sso/PZid）**，尚未打通 |

### 2.4 踩过的坑（务必记住）

1. **列表页是匿名的，不能发 `PZid` 头**。上一版报 `NOT_LOGGED_IN`（"登录失效"）的根因不是缺登录态，而是误发了 `waf_state` 里残留的过期 `PZid`。服务端看到 `PZid` 就按登录态校验 → 失效。去掉即成功。
2. **浏览器快照里的过期动态脚本会卡死 decode runner**。runner 里 `scriptSource` 优先级高于 `scriptPath`（固定脚本 `pz_decode_root_dynamic_script_latest.js`）：localStorage 里的 `_waf_a23a0b772` / `_waf_3d7faf79`（旧 WAF 脚本，103KB）一旦被当 `scriptSource` 传入就会优先执行 → 60s 超时。调用时别把这些旧 key 塞进 localStorage。
3. **`waf_state.json` 会过期**（跟出口 IP 绑定，之前过期 ~1 个月导致全挂）。刷新只需 ~0.5s，但要注意「WAF 状态是刷新来的，不是永久有效的」。
4. **签名是 v18 不是 v17**。版本由远程配置决定，`sign_utils` 会自动跟随，不要手写死。

## 三、螃蟹 (pxb7.com 鲸汐) 逆向

### 3.1 目标接口

| 用途 | 地址 | 是否要登录 |
|---|---|---|
| 商品列表 | `https://api-pc.pxb7.com/api/search/product/v2/selectSearchPageList` | ❌ 只要 `user_id` |
| 商品详情 | `https://api-pc.pxb7.com/api/product/web/product/detailPost` | ❌ |

### 3.2 逆出来的签名（`timestamp__1366`）

```
timestamp__1366 = "2790552d-" + u(LR)

LR = [ h1, h2, env, now, wafBd, wafATs, fpId ].join("|")

h1     = 哈希( encodeURIComponent(wafBd + methodLower + "2790552d" + canonicalUrl + body) )
h2     = 哈希( encodeURIComponent(wafBd + methodLower + "2790552d" + canonicalUrl) )
env    = 浏览器环境派生值（29 位随机数）
now    = 时间戳
wafBd  = localStorage _waf_bd8ce2ce37
wafATs = localStorage _waf_a86dfdc5f2
fpId   = 设备指纹 id（22 位 hex）
```

- 前缀 `2790552d` 是脚本写死的常量；参数名 `timestamp__1366` 里的 `1366` 由 hostname 字符码和派生（见 §3.3）。
- `u()` = LZ77 压缩 + 自定义 base64（把 7 字段压成一段密文串）。
- `Li`/`LS` 是自定义 64 位哈希（16 位 hex，非标准 MD5/SHA1）。

### 3.3 踩过的坑

1. **`env` / `fpId` 服务器都不校验具体值**，只要格式对（29 位随机数 / 22 位 hex）即可，无需还原真实浏览器的 `1310738` 之类。
2. **WAF token 与 IP 无关**（本地拿的 `_waf_bd8ce2ce37` 从神龙代理 IP 发同样返回真实 JSON）→ 不需要每个代理生成新 WAF，**全局单 token，~12h 过期或被杀时惰性刷新**即可。
3. **误判 h1/h2 错误的教训**：debugLog 模式下 `O`（MD5 轮函数）调试包装器只传单参、破坏哈希，导致误以为哈希不对；生产路径（无 debugLog）一直是对的。

### 3.4 代码地图

## 四、通用逆向套路（阿里云 WAF 一族）

两个平台底层是**同一套阿里云 WAF**，结构完全一致，只有前缀不同（螃蟹 `2790552d` / 盼之 `214d4f07715`）和哈希/压缩内部实现不同。下次遇到新的阿里云 WAF 站点，照着这个套路走：

### 4.1 三步定位签名

1. **抓包确认被拦**：请求不带 WAF 参数时，返回 200 但内容是 challenge 页（HTML 里含 `aliyun_waf` / `renderData`），说明有 WAF。
2. **浏览器里 hook 请求**：用 CDP（Chrome DevTools Protocol）在 `fetch`/`XMLHttpRequest` 上打断点/hook，找到「哪个函数给 URL 追加了 `timestamp__…` / `decode__…` 参数」。
3. **扣出混淆脚本 + 补环境**：把那段混淆 JS 抠出来，用一个 Node `vm` 沙箱补上 `window`/`navigator`/`location` 等环境，跑同一个函数，对比输出签名是否和抓包一致。

### 4.2 离线复现 vs 浏览器

| | 离线复现（本项目做法） | 浏览器 |
|---|---|---|
| 依赖 | Node + 静态脚本 | 无头浏览器 / CDP |
| 速度 | 毫秒级 | 秒级 |
| 稳定性 | 高（确定性 PRNG 注入） | 受浏览器版本/反检测影响 |
| 前提 | 需要一份真实会话的 WAF 状态（localStorage 几个 key） | 自动走 challenge |

关键：WAF 状态（`_waf_bd8ce2ce37` 等）是**挑战后**才有的，离线时要么从浏览器抓包拿一份初始值，要么用 `run_challenge()` 主动触发一次 challenge 刷新。

### 4.3 判断「随机字段要不要还原」

很多字段（`env`、`fpId`、`deviceId`）**服务端只验格式不验值**。判断方法：改一个随机值，请求还能过，就说明不校验。别浪费时间精确还原这些随机数。

## 五、新平台接入 Checklist

1. 浏览器抓包：列表接口的 URL / method / headers / body / 需要哪些签名参数。
2. 判断要不要登录态（有没有 token/cookie/sso）。
3. 定位签名函数（§4.1），扣脚本 + 补环境，用 Node runner 复现。
4. 处理 WAF 状态：初始值从抓包拿，运行时惰性刷新（检测到 challenge → 重刷 → 重试）。
5. 写 Python 桥（对齐 `sign_utils.generate_sign()` / `pxb7_waf.build_request_url()` 的接口风格）。
6. 写 `crawler_<平台>.py` + 在 `main_window.py` 加一行 `import`（参考 `docs/CRAWLER_INTEGRATION.md`）。

## 六、排障速查

| 现象 | 常见原因 |
|---|---|
| 返回 challenge 页（HTML 含 `aliyun_waf`/`renderData`） | WAF 状态过期 → 重刷 waf_state |
| `NOT_LOGGED_IN` | 误发 `PZid`（盼之列表页是匿名的） |
| decode 生成 30s 超时 | 浏览器快照里混入过期动态脚本 key → 排除 |
| 签名对不上抓包 | WASM 版本变了（盼之）→ 看 `wasm-config-prod.json` 的 `currentVersion` |
| 签名一直「h1/h2 不对」 | 可能是 debugLog 包装器单参破坏了哈希（螃蟹踩过） |
